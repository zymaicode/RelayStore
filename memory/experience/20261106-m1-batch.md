# 2026-11-06 · M1 一口气收口：JSON / Lua / catalog / resolver / verify / CLI / 报告

## 现象
M1 只剩「把所有零件串起来」：清单来源有 4 种 JSON 形态、Lua 要能改、库要幂等、源要能降级、CLI 要能离线查。
零散写会互相打架，一次成体系落地更省事。

## 关键设计（复用价值最高）
1. **形态识别按值判断，不按文件名**：tokens 与 depotkeys 都是「数字键 → 字符串值」的平表，
   只有值格式能区分（纯数字 = token；16~64 位偶数长 hex = depot key）。按文件名判会漏掉重命名文件。
2. **Lua 更新只改该改的行**：正则捕获原缩进与行尾注释，重建该行时原样拼回；未知行逐字保留。
   验收直接断言 diff 行数（2 行变化 = addappid + setManifestid），比「看起来对」可靠。
3. **幂等靠唯一键，不靠先查后写**：UNIQUE(appid,depot_id,gid) + ON CONFLICT DO UPDATE，
   重复导入不涨行；换 gid 自然成为历史行，history() 直接能回溯。
4. **降级要留证据**：每次 provider 尝试记 provider/ok/error/ms，失败也写进 attempts，
   最后要么返回 used=cache，要么抛 ResolveError 带上整条尝试链 —— 排障不用猜。
5. **缓存必须内容寻址 + 二次零请求**：hubcap 缓存文件名带 depot/gid/hash，测试断言 calls == 1。

## 踩到的坑
- SQL 字符串拼接时逗号写错位置：execute("A" "B", "C", params) 变成 3 个参数 → TypeError: execute expected at most 2 arguments。
  多行 SQL 用隐式拼接时只有最后一段带参数，逗号位置一眼看不出。
- 覆盖度扫描里 16 MB 的 depotkeys.json 能正常读，但要把「读不动 / 太大」用 -1 标出来，别让报告假装 0。

## 实测结论（对后续排期影响最大）
- 5 个 ManifestHub 快照里 .lua 文件数为 0 —— 仓库只发凭据 JSON（tokens / depotkeys），Lua 全靠客户端生成。
  所以 M2 的 lua_gen.py 不是锦上添花，是本体跑起来的必经环节。
- 镜像 kken26627 凭据最全（tokens 12576 / keys 469477），三个同源 fork 只有 5090 / 288381。
- CLI 离线查询 94 ms（含解释器启动），离 PRD 的 2 s 上限很远，不是瓶颈。

## 复用建议
- 批量交付时按「数据模型 → 解析 → 存储 → 编排 → 入口」顺序写，测试与实现各轮跑一次，失败面小。
- 门禁脚本对每个任务 ID 跑一次 gate-check.ps1，比最后一次性跑更有说服力（每个 ID 都有 PASS 记录）。
